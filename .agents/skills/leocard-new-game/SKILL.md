# LeoCard 新游戏开发

将用户已确定的新游戏或玩法模式接入现有 LeoCard 架构。只实现用户授权的范围；仅请求讨论或设计时不开始改代码。

## 开始前

1. 阅读项目根目录 AGENTS.md 和相邻的 [coding-conventions](../coding-conventions/SKILL.md)，按完整 12 条编码规范执行。
2. 检查工作区改动和用户提供的玩法文档。明确人数、合法动作、可见信息、阶段转换、计时、结束条件、分数及模式选项；只追问会改变玩法的歧义，已确认的解释继续有效。
3. 选一个结构最接近的已有游戏作参考，沿一条“命令 → 规则变化 → 事件／快照 → UI”的路径阅读。接入位置见 [references/integration-map.md](references/integration-map.md)，只读取本次需要的部分，路径以当前仓库为准。

## 各层职责

| 层 | 承担的工作 | 行为边界 |
|---|---|---|
| `crates/games/<game>/` | 规则、合法性校验、阶段状态机、结算事实、玩家可见视图和策略观测 | 保持纯游戏逻辑，不依赖 Bevy、网络、钱包、文件系统或客户端 UI；随机输入和时间推进须能受控 |
| `crates/protocol/` | 序列化规则、命令、事件、接收者快照与拒绝原因 | 描述公开接口，不实现游戏流程；不把隐藏手牌或答案泄露给无权查看者 |
| `crates/host/src/<game>/` | 将认证连接映射为玩家，驱动规则、计时和自动行动，发布事件／快照 | 房主权威；复用房间生命周期、重连和结算入口，不重复实现公共房间功能 |
| `crates/tcp/` | 传输、消息编解码和投递 | 游戏接入优先扩展会话后端，不把具体规则塞进 TCP 层 |
| 客户端 model 与 `app/games/<game>/` | 模型访问、规则配置、输入、桌面、动画和音效 | 根据权威快照展示，发送用户意图；不自行裁定胜负、积分或成就，也不把具体游戏内部状态塞进通用页面 |
| 成就与玩家存档 | 注册成就、消费合法事实、保存用户状态 | 各自封装；按用户要求接入，不为占位自行设计奖励或成就 |

## 规则与状态机

- 先贯通开局、合法行动、拒绝非法行动、结束和下一局。将一小局与整场进度区分，避免将“轮数”“总局数”“玩家轮次”混用。
- 对连锁响应、罚牌、交换等效果明确何时结算、何时允许继续响应、何时判胜。待结算的当前效果与未来回合的累计状态分开建模，避免提前结束或因未来状态无法结束。
- 同一游戏有多个模式时，使用模式类型和各自的配置结构；切换时保留每套配置，不让一个模式的开关或计时污染另一个模式。优先复用公共配置控件和模式下拉框。
- 机器人与托管使用清晰的独立入口，并按当前游戏约定选择策略；策略相同时可让一个入口调用另一个，不复制相同算法。自动行动仍通过合法规则接口，不能借用房主掌握的隐藏信息作弊。
- 真实时间由房主驱动，客户端展示同步结果。个人回合倒计时和整题／整局倒计时分开定义，不能因无关行动或重连错误重置。

## 联机与客户端接入

- 注册游戏种类、规则、命令、快照、事件和错误映射，接入房主会话分发、客户端模型投影、游戏目录、插件与页面组合。通过现有接口承接加入、断线、重连、准备、再玩一局及返回大厅。
- 快照负责当前状态和重连恢复，事件负责本次发生的事实。不要从重复快照重新触发奖励、成就、语音或已播放动画；按现有对局标识与事件序列去重。
- 每位接收者只能看到该玩家有权观察的数据。结算公开隐藏信息时，也要与对应阶段一致。
- 游戏专属 UI 与系统放在该游戏模块，公共组件放在公共表现层；复用头像、聊天、互动、设置和结算，不在各游戏手写偏移补丁或重复输入框逻辑。
- 使用项目现有文本编辑组件，保持焦点、IME、键盘和触摸行为；设置不可用时沿用公共控件的禁用外观，区分房主配置权限与具体选项是否可操作。
- 沿用现有 Bevy 系统集合和 UI 布局顺序，检查新增排序不会形成环。倒计时等瞬态更新优先局部刷新，不因每次计时重建整张牌桌。

## 按需求补齐公共能力

- **积分、金币和档案**：沿用公共结算接口与去重机制；复用房间对机器人局和开发者模式的记录策略。不要在游戏专属代码复制政策或直接修改客户端余额。
- **成就**：需求包含成就时，使用成就 crate 的注册表和触发器；游戏层产出可核验事实，成就条件在成就模块中求值。不要把底层事件收件箱泄露到通用页面状态。
- **存档与协议变更**：先检查修改是否改变 Postcard 存档或联机结构；不能假定新增字段的默认值就能读取旧二进制。需要兼容代码时先沿用会话已有决定或询问用户，迁移写入 migration 模块。线格式变更按现有版本协商更新协议版本。
- **素材与音效**：所有实际加载的路径都要进入 `crates/client/runtime-assets.txt`；仅复制文件或加测试路径不代表已内嵌。检查生成的内嵌清单，兼顾桌面 release 和 Android 的资源源。第三方素材记录来源并保留许可证；自生成素材无需写入 ASSETS.md。
- **素材生成工具**：脚本放在项目忽略的 `tools/` 中，不放 assets；只有运行时真正使用的资源进入素材目录。新游戏入口、风格、交互反馈和转场与现有游戏一致。

## 验证与交付

- 为核心状态机、非法动作、信息隔离、结算去重和关键边界写少量有效测试，优先扩展现有测试组织；不要给普通 UI 改动补机械测试。
- 按影响面做格式化、Clippy 和必要的核心验证；用户明确要求不运行测试时不运行。不要为新游戏默认启动客户端进行交互测试，交由用户体验；用户授权后再自行进游戏调试。
- 核对本次实际需要的接入点和 12 条编码规范，说明实现了什么、如何验证、哪些验证未运行以及尚未完成的授权内容。不要用仅有入口或仅通过编译代替可玩的完整链路。
